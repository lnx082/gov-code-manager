## 一、技术论述

### 1.1 测试策略与框架选型

#### 1.1.1 以 Node.js 内置测试框架替代第三方依赖

本系统测试框架未引入 Mocha、Jest 等第三方测试库，而是直接使用 Node.js 18+ 内置的 `node:test` 模块（[tests/auth.test.js:7](tests/auth.test.js#L7)），`describe`/`it`/`before`/`after` 语义与主流框架一致，零额外依赖。HTTP 请求层使用 Node.js 18+ 原生 `fetch` API（[tests/helpers/api.js:83](tests/helpers/api.js#L83)），断言层使用自实现的轻量 `assert` 对象（[tests/helpers/api.js:272-293](tests/helpers/api.js#L272-L293)），包含 `ok`、`equal`、`notEqual`、`match`、`greaterOrEqual`、`hasKeys` 六个核心方法。整个测试套件对第三方包的依赖为零，消除了供应链风险，也降低了测试环境的搭建成本。

#### 1.1.2 测试组织与执行模型

测试采用**模块化组织 + 统一入口**的双层结构：

- **模块层**：10 个独立测试文件，分别对应认证（A）、仓库（B）、分支（C）、合并（D）、版本（E）、基线（F）、归档（G）、审批（H）、审计（I）、安全越权（J）十个业务模块，共计 130+ 条测试用例。
- **统一入口**：[all.test.js](tests/all.test.js) 按依赖顺序聚合所有模块——认证模块最先执行以建立 token 缓存，安全越权模块最后执行以确保前置数据准备就绪。
- **全量执行器**：[run-all.js](tests/run-all.js) 提供单进程执行模式，支持 `--verbose`（spec 详细输出）、`--skip-gitea`（跳过 Gitea 依赖测试）、`--module=<name>`（单模块调试）三种运行模式。

聚合报告通过解析 TAP（Test Anything Protocol）格式输出实现，按模块前缀（A-至J-）分组统计通过/失败/跳过数量，并在失败时输出调试提示（[tests/run-all.js:218-295](tests/run-all.js#L218-L295)）。

### 1.2 Token 缓存与测试可靠性保障

#### 1.2.1 跨进程 Token 共享机制

系统测试覆盖四种角色（系统管理员 besti、项目管理员 YuxiangLiu、开发人员 lyx、审计人员 xhy），每种角色的测试用例都需要有效 JWT。为避免每个测试文件独立登录触发 `express-rate-limit` 限流（登录接口限制 5 次/分钟），测试框架实现了**文件级跨进程 Token 缓存**（[tests/helpers/api.js:15-53](tests/helpers/api.js#L15-L53)）：

```
临时文件 (os.tmpdir/govcode-test-tokens.json)
  └── { tokens: { admin: {token, user}, pm: {…}, … }, expiresAt: <5分钟> }
```

多进程启动时，后续进程从共享临时文件恢复已缓存的 token，避免重复登录。Token 缓存有效期 5 分钟，过期后自动重新登录刷新。

#### 1.2.2 登录节流与重试机制

测试辅助函数 `login()` 内置了**全局登录节流**（最小间隔 800ms + 随机抖动 200ms）和 **429 限流重试**（逐次递增等待：2s/4s/6s/8s + 随机抖动，最多 5 次），确保在服务端限流策略下仍能可靠完成所有测试账号的登录（[tests/helpers/api.js:132-164](tests/helpers/api.js#L132-L164)）。

#### 1.2.3 Token 预热

`run-all.js` 在所有测试模块启动前，依次登录四个测试账号将 token 写入共享文件（[tests/run-all.js:109-173](tests/run-all.js#L109-L173)），每次登录间隔 3 秒以上。预热完成后测试模块可直接从共享文件读取 token 而无需再次登录，从架构层面规避了限流导致测试不稳定的问题。

### 1.3 测试覆盖维度

#### 1.3.1 认证授权覆盖

认证模块（12 条用例）覆盖了完整登录生命周期：四种角色正常登录（A-01a~d）、空参数校验（A-02）、错误密码拒绝（A-03）、无 Token 拦截（A-04）、过期 Token 处理（A-05，使用手工构造的过期 JWT）、伪造 Token 拒绝（A-06）、Query 参数 Token 支持（A-07，用于下载场景）、正常登出（A-08）、`/auth/me` 用户信息获取（A-09a~c）、已注销用户拦截（A-10）、账号锁定拦截（A-11）、本地密码兜底认证（A-12）。其中 A-10/A-11/A-12 为代码级逻辑验证——因无法在生产数据库上随意修改 `is_active`/`account_locked` 状态，采用代码路径分析方式确认对应分支逻辑存在。

#### 1.3.2 权限越权覆盖

安全越权模块（21 条用例）按**角色×端点×操作**三维矩阵设计，覆盖四类越权场景：

- **横向越权**：审计人员/开发人员尝试查看用户列表（J-03a~c）、修改他人信息（J-05a~b，IDOR 测试）
- **垂直越权**：开发人员尝试创建角色（J-04a~b）、修改系统配置（J-06a~c）、访问备份管理（J-07a~c）、冻结基线（J-08）
- **权限边界验证**：审计人员访问审计端点（J-02a~b）、管理员万能权限验证（J-09，10 个管理端点全量验证）
- **数据隔离验证**：部门密级过滤——非管理员审批列表数量 ≤ 管理员审批列表数量（J-10），前端路由白名单限制（J-11）

测试代码中标注了已知 BUG（[tests/security.test.js:60-62](tests/security.test.js#L60-L62)），如 C-10（`GET /users` 缺少 `requireAdmin`）、C-08（`baselines freeze` 缺少角色检查），当测试发现越权成功时输出标注日志而非直接断言失败，实现了**测试即文档**的效果。

#### 1.3.3 审计链完整性覆盖

审计模块（11 条用例）不仅验证了 CRUD 操作和 CSV 导出（含 BOM 头检测、中文表头验证），更重要的是对 **SHA-256 防篡改审计链**做了端到端验证（I-05）：从审计日志列表取首尾两条记录作为区间参数，调用 `/audit/logs/verify-integrity` 接口，验证 `isValid` 字段和 `invalidLogs` 数组的正确性（[tests/audit.test.js:66-79](tests/audit.test.js#L66-L79)）。

#### 1.3.4 审批流程覆盖

审批模块（18 条用例）覆盖了完整的审批生命周期：审批列表查询、待我审批（三种角色各自验证）、创建审批申请（三种角色分别发起）、多步流程阶段性审批（第 1 步通过后 `current_step` 递进）、最后一步通过后后置操作执行、重复审批拦截、审批统计、流程模板 CRUD、建议流程匹配、带进行中审批单的流程删除保护。

#### 1.3.5 Gitea 依赖可选化

通过 `TEST_SKIP_GITEA` 环境变量控制是否跳过依赖 Gitea 连接的测试（仓库创建、分支操作、PR 合并等），`skipIfNoGitea()` 辅助函数在 Gitea 不可用时自动标记用例为跳过而非失败（[tests/helpers/api.js:261-266](tests/helpers/api.js#L261-L266)），保证了测试套件在仅 BFF + 数据库可用的环境下仍可执行核心业务测试。

### 1.4 测试数据管理

#### 1.4.1 测试配置集中化

所有测试配置（BFF 地址、超时时间、四种角色账号密码、默认仓库、请求间隔）集中在 [config.js](tests/config.js) 中，全部支持环境变量覆盖（如 `TEST_BASE_URL`、`TEST_ADMIN_USER`、`TEST_SKIP_GITEA`），在不修改代码的情况下适配不同部署环境。

#### 1.4.2 仓库自动发现

`getFirstRepo()` 函数（[tests/helpers/api.js:223-247](tests/helpers/api.js#L223-L247)）优先使用环境变量配置的仓库，否则自动从管理员仓库列表选取第一个可用仓库，避免硬编码仓库名导致的测试脆弱性。

## 二、创新意识体现

### 2.1 零外部依赖的测试架构

有别于业界普遍依赖 Jest/Mocha/Chai 等 NPM 包的惯例，本系统测试框架完全基于 Node.js 内置能力构建：`node:test` 提供测试组织结构，原生 `fetch` 提供 HTTP 通信，自实现 `assert` 提供断言语义。这一选择有三重效果：一是消除了 npm 供应链攻击面，测试阶段不引入任何不可信代码；二是测试环境搭建简化为仅需 Node.js 18+ 运行时；三是测试执行不经过任何 transpiler/loader 层，行为与生产运行时完全一致，消除了"测试能过但生产报错"的工具链差异风险。

### 2.2 跨进程 Token 共享与限流友好型测试

在常规 API 测试中，多角色测试面临的核心矛盾是：测试需要频繁切换身份（四种角色 × 数十条用例），但登录接口的限流策略（5 次/分钟）使得逐条登录不可行。本系统的解决方案体现了创新思路——通过 `os.tmpdir()` 文件实现**跨进程 Token 共享**，配合 `run-all.js` 的**账号预热机制**和单进程顺序执行策略，将实际操作中的登录次数从潜在的数十次压缩为预热阶段的 4 次。同时，登录辅助函数内置了**自适应限流处理**（429 → 等待 → 递增重试），使测试在限流严格的环境下仍能稳定完成。这一"测试适应限流而非绕过限流"的设计思路，确保了测试的可靠性与安全策略的一致性——如果在测试中绕过限流，就无法验证限流机制本身是否正常工作。

### 2.3 已知 BUG 标注与测试即文档

测试代码中并非简单地对所有不符合预期的情况断言失败，而是区分了"预期正确行为"和"已知缺陷"——当发现越权成功时，测试输出 `[已知BUG C-10] GET /users 缺少 requireAdmin` 等标注日志（[tests/security.test.js:60-62](tests/security.test.js#L60-L62)），而非直接使测试失败。这种设计使测试报告同时成为**活的缺陷清单**：一眼就能区分哪些是本次修改引入的新回归、哪些是已记录的已知问题。相比于将已知 BUG 列在单独的 Excel 或 Markdown 文档中的传统做法，这种方式天然避免了文档与代码不同步的问题。

### 2.4 TAP 协议解析与聚合报告生成

`run-all.js` 没有使用第三方测试报告器，而是通过解析 Node.js 内置 TAP 输出格式，按模块前缀（A-至J-）分组统计，生成包含模块级通过率、失败详情、调试提示的结构化聚合报告（[tests/run-all.js:218-295](tests/run-all.js#L218-L295)）。这种"用标准的机器可读格式 + 轻量解析层替代重量级报告框架"的思路，既保证了报告的可定制性，又没有增加依赖负担。

### 2.5 审批流程的端到端业务闭环测试

审批模块（H-01~H-12）不仅是单接口的输入输出验证，而是构建了一个完整的业务流程闭环：三种角色各自发起审批申请 → 验证自动关联默认流程 → 多步流程阶段性审批 → 验证 `current_step` 递进 → 最后一步通过后的后置操作触发。这种将"创建→处理→状态流转→后置操作→统计汇总"作为一个连续业务流进行验证的方式，比孤立地测试每个接口更能暴露流程衔接处的缺陷。

## 三、非技术因素考虑

### 3.1 政治因素

#### 3.1.1 党政机关使用场景的合规性验证

本系统的最终用户为党政机关，测试设计中明确覆盖了与党政机关业务规范对齐的验证点。审计人员路由白名单测试（[tests/security.test.js:236-241](tests/security.test.js#L236-L241)）——验证审计人员仅能访问 `/dashboard`、`/profile`、`/settings`、`/audit/*` 六个页面——其背后对应的是党政机关"审计独立、权限分离"的组织原则。审批流程的多级递进测试（H-04/H-05）对应党政机关的逐级审批制度，确保技术实现与行政管理体制一致。四角色权限矩阵的全面覆盖测试，验证了系统权限模型与党政机关"三员分立"（系统管理员、安全保密员、安全审计员）的安全管理要求对齐。

#### 3.1.2 国产化技术栈的测试兼容性

系统在 openGauss 国产数据库上运行，测试框架未使用任何绑定特定数据库驱动的测试工具，所有数据库操作通过 Knex.js 的参数化查询完成，确保测试在国产化环境下的可移植性。`TEST_SKIP_GITEA` 环境变量支持在国产内网环境（无 Gitea 连接）下执行核心业务测试，适配党政机关内外网隔离的部署场景。

### 3.2 安全因素

#### 3.2.1 安全机制的验证覆盖

测试用例直接验证了系统中多项安全机制的运行状态。登录限流的验证——测试框架主动适应限流而非绕过，实际确认了 `express-rate-limit` 在生产环境中对暴力破解的防护效果。JWT 认证链的完整测试（A-04 无 Token、A-05 过期 Token、A-06 伪造 Token）验证了身份认证的不可绕过性。SHA-256 审计链完整性校验测试（I-05）验证了防篡改机制的真实可用性，而非仅存在于设计文档中。CSV 导出 BOM 头检测（I-07a）确保了审计数据导出后在 Excel 中中文不乱码，这在党政审计场景中是实际可用性的前提。

#### 3.2.2 默认凭据使用的测试警示

测试配置中的硬编码密码（[tests/config.js:19-40](tests/config.js#L19-L40)，`huawei666`）真实反映了生产环境中的凭据管理问题。测试代码在注释中明确标注"密码统一: huawei666"，配合 `run-all.js` 启动时的账号明文输出（[tests/run-all.js:71-76](tests/run-all.js#L71-L76)），形成了一种隐式的安全提醒——如果测试人员能在控制台看到明文密码，那么生产环境中这些凭据也应被替换。

#### 3.2.3 越权测试对安全审计的支撑

安全越权模块（J-01~J-11）系统的覆盖了**横向越权**（同角色操作他人数据，J-05a~b IDOR 测试）、**垂直越权**（低权限角色操作高权限功能，J-03/J-04/J-06/J-07）、**权限边界**（审计人员端点白名单，J-02/J-11）三个维度。测试中标注的已知 BUG（C-10 `GET /users` 缺少 `requireAdmin`、C-08 基线冻结缺少角色检查）直接为安全审计提供了整改优先级排序的客观依据——哪些缺口在测试阶段已经被发现、哪些是新增风险。

### 3.3 法律因素

#### 3.3.1 审计日志留存合规验证

《网络安全法》第二十一条和等保 2.0 标准要求网络日志留存不少于六个月。系统审计日志默认留存 3650 天（10 年），测试用例 I-01~I-08 完整覆盖了日志的记录（I-08 自动写入验证）、查询（I-01~I-04 多维度过滤）、导出（I-07 CSV 导出含 UTF-8 BOM）和完整性校验（I-05 SHA-256 哈希链验证）全链路。审计日志 CSV 导出功能测试验证了 BOM 头和中文字段名，确保在监管机构要求提供审计数据时，系统能够输出符合格式要求的可读数据。

#### 3.3.2 个人信息保护

《个人信息保护法》要求对个人信息实施访问控制。权限越权测试中专门设计了 IDOR（不安全直接对象引用）测试（J-05a~b），验证非管理员用户无法通过修改 URL 中的 `user_id` 参数来篡改他人信息。尽管测试发现了 C-10（`GET /users` 缺少 `requireAdmin`）的权限缺口，但 `PUT /users/:id` 的越权测试确认了修改操作已被中间件保护，数据写入防线有效。这种"读权限放行、写权限拦截"的分层防护现状在测试报告中得到了精确刻画，为后续整改提供了精准定位。

### 3.4 社会与文化因素

#### 3.4.1 政务办公习惯的测试适配

系统 UI 涉及政务风格元素（红色主题、国徽图标、"为人民服务"欢迎语、农历日期），虽然这些前端 UI 组件不属于白盒 API 测试的直接范围，但审计模块 CSV 导出测试（I-07）专门验证了 UTF-8 BOM 头和中文字段名的正确性——这在党政机关的实际工作中至关重要：审计数据导出后需要在国产办公软件（如 WPS）中正确显示中文，BOM 头的缺失将导致乱码。这一测试细节体现了对基层政务办公环境的关注。

#### 3.4.2 四种角色的测试覆盖体现了组织分工

测试框架按四种党政机关典型角色组织测试（系统管理员、项目管理员、开发人员、审计人员），而非按技术角色（如"超级用户""普通用户"）划分。这种角色设计映射了党政机关的实际组织架构和审批链，测试用例的角色编排与真实使用场景中的人员分工一致，使得测试报告（哪些角色能做什么操作、不能做什么操作）可以直接作为系统使用手册的权限说明部分。

### 3.5 环境因素

#### 3.5.1 国产化环境的测试兼容性

系统目标部署环境为国产化组合（麒麟/鲲鹏操作系统 + openGauss 数据库），测试框架在设计上考虑了国产环境的约束：一是零额外依赖确保在受限网络（国产环境通常不能自由访问 npm registry）下也能运行测试；二是通过 `TEST_SKIP_GITEA` 环境变量支持内外网隔离场景——内网测试仅需 BFF+数据库即可执行全部核心业务测试，无需外网 Gitea 连接；三是所有环境变量支持通过 `export` 覆盖，适配不同环境下的部署参数差异。

#### 3.5.2 测试对运行环境的友好性

Token 缓存使用 `os.tmpdir()` 而非工作目录，避免了测试运行在只读文件系统上的兼容性问题。登录节流（[tests/helpers/api.js:132-139](tests/helpers/api.js#L132-L139)）在保护服务端不被测试压力压垮的同时，也避免了测试客户端因请求过于密集而触发操作系统层面的连接限制。这些细节设计使得测试套件能够在从开发笔记本到堡垒机再到 CI Runner 等多种环境下稳定运行。

/**
 * 测试辅助函数
 * 封装 API 请求、登录、断言等常用操作

import { BASE_URL, TIMEOUT, TEST_ACCOUNTS, TEST_REPO, REQUEST_DELAY, SKIP_GITEA, VERBOSE } from '../config.js';

// ─── 认证状态缓存 ─────────────────────────────────────────
const tokenCache = new Map();       // accountKey → token
const userInfoCache = new Map();    // accountKey → userInfo
let cachedFirstRepo = null;         // 自动发现的第一个仓库
let lastLoginTime = 0;              // 上次登录时间戳（全局节流）
const LOGIN_THROTTLE_MS = 800;     // 登录最小间隔（避免触发限流）

// ─── 共享token文件（跨进程缓存） ─────────────────────────
import { existsSync, readFileSync, writeFileSync } from 'fs';
import { tmpdir } from 'os';
import { join } from 'path';

const TOKEN_FILE = join(tmpdir(), 'govcode-test-tokens.json');

function readSharedTokens() {
  try {
    if (existsSync(TOKEN_FILE)) {
      const data = JSON.parse(readFileSync(TOKEN_FILE, 'utf-8'));
      if (data.expiresAt && Date.now() < data.expiresAt) {
        return data.tokens || {};
      }
    }
  } catch { /* ignore */ }
  return {};
}

function writeSharedTokens(tokens) {
  try {
    writeFileSync(TOKEN_FILE, JSON.stringify({
      tokens,
      expiresAt: Date.now() + 300_000, // 5分钟有效
      savedAt: new Date().toISOString()
    }, null, 2));
  } catch { /* ignore */ }
}

// 启动时从文件恢复缓存
(function restoreFromFile() {
  const shared = readSharedTokens();
  for (const [key, info] of Object.entries(shared)) {
    if (info.token) {
      tokenCache.set(key, info.token);
      userInfoCache.set(key, info.user);
    }
  }
})();

/**
 * 发起API请求（自动附加Authorization）
 */
export async function apiRequest(method, path, options = {}) {
  const { body, token, rawResponse = false } = options;
  const headers = { 'Content-Type': 'application/json' };
  if (token) { headers['Authorization'] = `Bearer ${token}`; }

  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(), TIMEOUT);

  try {
    const res = await fetch(`${BASE_URL}${path}`, {
      method, headers,
      body: body ? JSON.stringify(body) : undefined,
      signal: controller.signal,
    });
    clearTimeout(timer);

    if (rawResponse) { return res; }

    const contentType = res.headers.get('content-type') || '';
    if (contentType.includes('application/json')) {
      const data = await res.json();
      return { status: res.status, headers: res.headers, ...data };
    }
    const text = await res.text();
    return { status: res.status, headers: res.headers, body: text };
  } catch (error) {
    clearTimeout(timer);
    if (error.name === 'AbortError') {
      throw new Error(`请求超时: ${method} ${path} (${TIMEOUT}ms)`);
    }
    throw error;
  }
}

/**
 * 登录并缓存token（支持全部四种角色）
 * 内置登录节流 + 429自动重试，避免触发服务端限流
 */
export async function login(accountKey = 'admin') {
  const account = TEST_ACCOUNTS[accountKey];
  if (!account) throw new Error(`未找到测试账号: ${accountKey}`);

  // 检查缓存
  if (tokenCache.has(accountKey)) {
    return {
      token: tokenCache.get(accountKey),
      user: userInfoCache.get(accountKey),
      account,
    };
  }

  // ── 登录节流 ──
  const now = Date.now();
  const gap = now - lastLoginTime;
  if (gap < LOGIN_THROTTLE_MS) {
    const waitMs = LOGIN_THROTTLE_MS - gap + Math.random() * 200;
    await delay(waitMs);
  }

  // ── 带重试的登录（处理429限流） ──
  let result;
  for (let attempt = 0; attempt < 5; attempt++) {
    lastLoginTime = Date.now();
    result = await apiRequest('POST', '/auth/login', {
      body: { username: account.username, password: account.password },
    });

    if (result.code === 200) break;

    if (result.code === 429) {
      const waitMs = 2000 * (attempt + 1) + Math.random() * 1000;
      await delay(waitMs);
      continue;
    }
    break;
  }

  if (result.code !== 200) {
    throw new Error(
      `登录失败 [${accountKey}] ${account.username}: ` +
      `code=${result.code} message="${result.message || JSON.stringify(result)}"`
    );
  }

  const token = result.data?.token;
  const user = result.data?.user;
  if (!token) { throw new Error(`登录失败 [${accountKey}]: 响应中无token`); }

  tokenCache.set(accountKey, token);
  userInfoCache.set(accountKey, user);

  // 写入共享文件，供其他进程读取
  const allTokens = {};
  for (const [k, v] of tokenCache) {
    allTokens[k] = { token: v, user: userInfoCache.get(k) };
  }
  writeSharedTokens(allTokens);

  return { token, user, account };
}

/**
 * 使用指定角色登录并返回带有 Authorization 头的请求函数
 */
export async function asUser(accountKey = 'admin') {
  const { token, user } = await login(accountKey);
  return {
    token, user,
    get:  (path)        => apiRequest('GET', path, { token }),
    post: (path, body)  => apiRequest('POST', path, { token, body }),
    put:  (path, body)  => apiRequest('PUT', path, { token, body }),
    del:  (path)        => apiRequest('DELETE', path, { token }),
    rawGet:  (path)       => apiRequest('GET', path, { token, rawResponse: true }),
    rawPost: (path, body) => apiRequest('POST', path, { token, body, rawResponse: true }),
  };
}

/**
 * 简单断言包装器
 */
export const assert = {
  ok(value, msg) {
    if (!value) throw new Error(msg || `断言失败: 期望 truthy, 实际 ${value}`);
  },
  equal(actual, expected, msg) {
    if (actual !== expected) throw new Error(msg || `断言失败: 期望 ${expected}, 实际 ${actual}`);
  },
  notEqual(actual, expected, msg) {
    if (actual === expected) throw new Error(msg || `断言失败: 期望不等于 ${expected}`);
  },
  match(str, regex, msg) {
    if (!regex.test(str)) throw new Error(msg || `断言失败: "${str}" 不匹配 ${regex}`);
  },
  greaterOrEqual(actual, min, msg) {
    if (actual < min) throw new Error(msg || `断言失败: ${actual} < ${min}`);
  },
  hasKeys(obj, keys, msg) {
    for (const k of keys) {
      if (!(k in obj)) throw new Error(msg || `断言失败: 对象缺少字段 "${k}"`);
    }
  },
};

export function delay(ms = REQUEST_DELAY) {
  return new Promise(resolve => setTimeout(resolve, ms));
}

  tokenCache.clear();
  userInfoCache.clear();
