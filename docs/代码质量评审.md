## 一、致命问题（必须立即修复）

### 1.1 硬编码凭据 + 生产环境安全检查被注释

**文件**: [bff/src/config/index.js:113-141](bff/src/config/index.js#L113-L141)、[bff/.env](bff/.env)、[bff/.env.example](bff/.env.example)

**问题描述**:

源码中硬编码了多个敏感凭据：

| 凭据 | 硬编码值 | 位置 |
|------|----------|------|
| JWT 签名密钥 | `gov_code_manager_jwt_secret_key_2024_secure` | `config/index.js:113`、`.env:19` |
| 数据库密码 | `Besti@2026_db` | `.env:10`、`.env.example:18` |
| Gitea 管理员 Token | `Basic YmVzdGk6aHVhd2VpNjY2` | `.env:16` |

`Basic YmVzdGk6aHVhd2VpNjY2` 经 base64 解码后为 `besti:huawei666`，即 Gitea 管理员用户名密码明文。攻击者获取该 token 后可对 Gitea 执行任意操作。

更严重的是，**生产环境凭据验证代码被整段注释掉**（`config/index.js:125-141`），系统将以 `NODE_ENV=production` 启动却不会阻止默认凭据的使用。安全兜底机制被人为禁用。

```javascript
// 第125-141行：被注释的生产环境凭据检查
if (config.nodeEnv === 'production') {
  const missing = [];
  // if (!process.env.JWT_SECRET || ...) { missing.push('JWT_SECRET...'); }
  // if (!process.env.DB_PASSWORD || process.env.DB_PASSWORD === 'Besti@2026_db') { ... }
  // if (!process.env.GITEA_ADMIN_TOKEN || process.env.GITEA_ADMIN_TOKEN === 'Basic...') { ... }
  if (missing.length > 0) { ... process.exit(1); }
}
```

**修复建议**: 
1. 从所有文件中删除硬编码凭据，改用环境变量且不设默认值
2. 取消生产环境检查的注释，确保部署时强制设置凭据
3. `.env` 和 `.env.example` 加入 `.gitignore`（如果已提交，需要轮换所有凭据并清理 Git 历史）
4. `docker-compose.yml` 和 `init-data.sql` 中的硬编码 IP `123.60.219.19` 也应移除

### 1.2 用户密码明文写入审计日志（持久化存储）

**文件**: [bff/src/middleware/audit.js:135](bff/src/middleware/audit.js#L135)

**问题描述**: 审计中间件拦截所有 API 请求并将 `req.body` 原样存入 `audit_logs` 表的 `request_body` 字段（截取前 4000 字符）。登录请求 (`POST /api/bff/auth/login`) 的请求体包含 `{ username, password }`，用户的明文密码被持久化写入数据库。

```javascript
// audit.js:135
request_body: JSON.stringify(req.body || {}).substring(0, 4000),
```

这意味着：
- 数据库管理员可以看到所有用户的明文密码
- 审计日志导出时密码随之泄露
- 违反等保对敏感信息保护的要求

**修复建议**: 在记录 `request_body` 前过滤 `password`、`oldPassword`、`newPassword`、`token` 等敏感字段。

### 1.3 操作符优先级 Bug — 文件差异计算的条件逻辑错误

**文件**: [bff/src/routes/gitea.js:48](bff/src/routes/gitea.js#L48)

**问题描述**: JavaScript 中 `&&` 优先级高于 `||`，导致这行代码的实际执行逻辑与预期不符：

```javascript
// 原代码（错误）
} else if (f.status === 'removed' || f.status === 'deleted' && parentSha) {

// 实际等价于
} else if (f.status === 'removed' || (f.status === 'deleted' && parentSha)) {

// 正确写法
} else if ((f.status === 'removed' || f.status === 'deleted') && parentSha) {
```

当 `f.status === 'removed'` 时，即使 `parentSha` 为空字符串也会进入该分支，向 Gitea 发起对不存在父提交的 fetch 请求，导致静默失败和文件变更内容丢失。

**修复建议**: 添加括号明确优先级：`(f.status === 'removed' || f.status === 'deleted') && parentSha`

### 1.4 Knex 查询缺少 `.first()` — 导致用户信息永远加载失败

**文件**: [bff/src/routes/users.js:73-78](bff/src/routes/users.js#L73-L78)

**问题描述**: Knex 在不使用 `.first()` 时返回数组（即使是空数组 `[]`），而空数组是 truthy 值：

```javascript
const profile = await db('user_profiles')
    .select('user_profiles.*', 'departments.name as department_name')
    .leftJoin('departments', 'user_profiles.department_id', 'departments.dept_id')
    .where('user_id', req.user.userId)   // ← 缺少 .first()！

if (!profile) {
    // ← 永远不会进入此分支！Knex 返回数组，即使是空数组也是 truthy
    return res.status(404).json({ code: 404, message: '用户不存在' });
}
```

后果：查询无结果时不会返回 404，后续 `profile?.nickname` 等字段均为 `undefined`，`/api/bff/users/me` 端点返回的用户信息缺失。

**修复建议**: 在 `.where(...)` 后添加 `.first()`。

### 1.6 API 层函数严重重复 — 三套并行封装

**问题描述**: 前端 API 层存在三个互相独立且功能重叠的封装：

| 层级 | 核心文件 | Axios 实例 | 函数数量 |
|------|---------|-----------|---------|
| 新层 | `api/bff.js` | `bffService` | ~80 |
| 旧层 | `api/admin.js` + `api/approval.js` + `api/audit.js` + `api/version.js` | `request` | ~40 |
| Gitea代理 | `api/gitea.js` | `giteaService` | ~60 |

此外，`api/merge.js:22-29` 的两个函数在第 37-43 行被重新定义覆盖，前两个是死代码。

**修复建议**: 统一为单一 API 层，删除旧层和碎片层文件。所有调用方从唯一入口导入。

## 三、中危问题（建议修复）

### 3.1 密码明文以 base64 形式长期驻留服务端内存

**文件**: [bff/src/services/credentialStore.js](bff/src/services/credentialStore.js)、[bff/src/routes/auth.js:371-411](bff/src/routes/auth.js#L371-L411)

```javascript
// credentialStore.js
const credentialStore = new Map(); // userId → Basic base64(username:password)

// auth.js
async function createGiteaToken(username, password) {
    const credentials = Buffer.from(`${username}:${password}`).toString('base64');
    return `Basic ${credentials}`;  // 密码的 base64 编码（非加密）
}
```

所有在线用户的 Gitea 密码以 base64（可逆编码，非加密）形式存储在内存 Map 中。服务重启前一直存在。有内存 dump 访问权限的攻击者可获取所有活跃用户的明文密码。`credentialStore` 无 TTL 过期策略，Map 无限增长。

**修复建议**: 使用 Gitea Access Token 替代 Basic Auth。短期方案至少为 credentialStore 添加 TTL 过期机制。

### 3.2 `apiLimiter` 已定义但未应用到任何路由

**文件**: [bff/src/middleware/rateLimiter.js](bff/src/middleware/rateLimiter.js)

`apiLimiter`（每分钟 100 次）已定义，但仅在登录路由上使用了 `authLimiter`。所有业务 API（用户列表、密码修改、CRUD 操作）均无应用层速率限制。配置中的 `maxLoginAttempts` 和 `lockoutDuration` 也未与实际的账户锁定逻辑连通。

**修复建议**: 对所有业务路由应用 `apiLimiter`，对敏感端点（改密、用户创建/删除）使用更严格的限制。

### 3.3 客户端分页导致数据截断和分页不一致

**文件**: [front/src/views/branches/merge.vue:391-445](front/src/views/branches/merge.vue#L391-L445)

```javascript
const params = { page: 1, pageSize: 200 }  // 仅取前 200 条
```

**修复建议**: 改为服务端分页，筛选状态变更时重置 `page = 1`。

## 四、低危和代码质量问题

### 4.1 前端巨型组件

| 文件 | 行数 | 问题 |
|------|------|------|
| [front/src/views/branches/merge.vue](front/src/views/branches/merge.vue) | 1,023 | 混合了列表、创建对话框、详情对话框、审批对话框、合并逻辑 |
| [front/src/views/dashboard/index.vue](front/src/views/dashboard/index.vue) | 876 | 混合了统计、ECharts、系统状态、通知发布、快捷链接 |
| [front/src/App.vue](front/src/App.vue) | 821 | 混合了布局、通知弹窗、详情弹窗 |

**建议**: 抽取为 composables 或子组件。merge.vue 至少可拆分为 `MergeRequestList`、`CreateMergeDialog`、`MergeDetailDialog`、`ApprovalDialog` 四个组件。

### 4.2 静默异常吞没

整个代码库中存在 30+ 处空的或仅含注释的 catch 块：

```javascript
} catch { /* 获取失败则显示全部 */ }
} catch { /* Gitea 补充失败不影响主数据 */ }
} catch { /* ignore */ }
} catch (_) { /* ignore */ }
.catch(() => {})
```

没有错误日志的异常吞没使问题排查极其困难。部分静默异常掩盖了重要错误（如权限不足但被忽略）。

### 4.3 Mock 数据库静默降级

**文件**: [bff/src/database/connection.js:228-231](bff/src/database/connection.js#L228-L231)

数据库连接失败时自动降级为空内存 Mock，所有查询返回空、写操作静默忽略。生产环境会导致"系统正常运行但数据全空"的不可解释状态。

### 4.4 数据库迁移逻辑重复

### 4.8 前端客户端假验证码

**文件**: [front/src/views/login.vue:149-155](front/src/views/login.vue#L149-L155)（死代码假登录页面中）

该文件中包含一个完全在客户端生成和校验的"验证码"逻辑——验证码值在客户端随机生成并绘制到 Canvas，校验也在客户端完成。这种验证码提供**零安全价值**，仅增加视觉复杂度，对自动化脚本攻击毫无防御力。

### 4.9 直接访问 sessionStorage 绕过统一 Token 管理

以下三个文件直接调用 `sessionStorage.getItem('gitea_token')` 读取 token，绕过了 [api/index.js](front/src/api/index.js) 中统一的 `getToken()` 封装：

一旦 storage key 名称变更或 token 格式调整，这些位置将静默失效。应统一通过 `@/api` 的 `getToken()` 获取。

### 4.10 `window.open()` 缺少 `noopener/noreferrer` — Tabnabbing 风险

以下三处使用 `window.open(url, '_blank')` 但未传递 `noopener,noreferrer`：

| 文件 | 行号 |
|------|------|
| [utils/download.js](front/src/utils/download.js) | 46 |
| [views/audit/reports.vue](front/src/views/audit/reports.vue) | 347 |
| [views/repos/detail.vue](front/src/views/repos/detail.vue) | 500 |

缺少 `noopener` 意味着新打开的页面可以通过 `window.opener` 操纵当前页面，可能被用于钓鱼攻击（Tabnabbing）。正确写法应为：

```javascript
window.open(url, '_blank', 'noopener,noreferrer')
```

### 4.12 其他零散问题

- **状态映射重复定义**: 角色名称映射（admin→系统管理员 等）在 [stores/user.js](front/src/stores/user.js)、[routes/auth.js:131-133](bff/src/routes/auth.js#L131-L133)、[routes/auth.js:332](bff/src/routes/auth.js#L332) 至少 3 处独立硬编码，修改时极易遗漏
- **登录后重复请求**: [login/index.vue:113-115](front/src/views/login/index.vue#L113-L115) 中 `loginAction` 已设置 `userInfo`，紧接着 `initUser()` 再发一次 `/auth/me` 获取同样的信息
- **重复的 `loadSourceBranches` / `loadTargetBranches`**: [merge.vue:471-493](front/src/views/branches/merge.vue#L471-L493) 两个函数除一个变量名不同外完全一致
- **`removed`/`deleted` 状态文案不一致**: 前后端混用两种表达方式
- **`N+1` 请求爆炸**: [merge.vue:410-437](front/src/views/branches/merge.vue#L410-L437) 对 200 条数据中的每条发起 2 个 Gitea API 调用，共计 400 并发请求，无分批和缓存
- **`.then()` 与 `async/await` 混用**: [App.vue:329-337](front/src/App.vue) 在 `.then()` 回调中使用 `async/await`，嵌套混乱
- **开发环境 JWT secret 随机化**: [config/index.js:114](bff/src/config/index.js#L114) 开发模式每次重启用 `crypto.randomBytes(32)` 生成新密钥，所有现存 token 立即失效
- **数据库迁移逻辑重复**: `fixDatabaseSchema`、`runMigrations`、`seedDefaultData` 三个函数在 [connection.js](bff/src/database/connection.js) 中重复创建相同的表和插入相同的默认数据
- **前端 .env 文件暴露内网 IP**: [front/.env](front/.env) 和 [front/.env.production](front/.env.production) 中硬编码 `123.60.219.19`
